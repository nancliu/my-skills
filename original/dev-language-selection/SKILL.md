# 多语言选型（项目落地版）

立项、技术评审、方案选型时按本技能做语言决策。完整对照表见 [language-matrix.md](language-matrix.md)。

## When to use

- 新项目问「用什么语言」
- 技术评审需要语言选型结论与理由
- 对比 Ruby / Python / Go / Java / C/C++ / Rust / Kotlin
- 讨论 GUI、并发、交付形态、流式计算分层混搭

**When NOT to use**：纯框架选型（如 Spring vs Rails）、纯模型选型、与开发语言无关的基础设施选型。

## Steps

1. **收需求**：交付物（Web / GUI / 服务 / 库）、并发与延迟、部署约束、团队背景、是否强监管/长期多人维护。信息不足先问，不猜。
2. **对照决策规则**（见下节）得到主选语言；需要细节时读 [language-matrix.md](language-matrix.md)。
3. **判断是否混搭**：工业常态是分层（脚本/工具、网关/agent、核心交易/流式、底层硬件）各选一门，不必单语言通吃。
4. **输出选型结论**（模板见下），含主选、备选、明确不选及原因。

## 决策规则（评审直接用）

1. 界面是交付重点、给普通用户使用 → **Python**
2. 核心是业务 Web、需要灵活 DSL、小团队快速迭代 → **Ruby**
3. 做平台/网关/agent、大量并发连接、要求交付简单、单二进制 → **Go**
4. 金融、强监管、核心交易、Flink 流式计算、多人长期维护大型系统 → **Java**（或 Flink SQL 规避手写 Java）
5. 碰硬件、驱动、内核、编解码、极致低延迟底层模块 → **C/C++**
6. 想要 C 的性能，又不想承担野指针风险，团队愿意啃陡峭学习曲线 → **Rust**

冲突时：先定「交付形态与核心瓶颈」（GUI / 并发连接 / 监管交易 / 硬件底层），再用规则裁决；仍冲突则给主选 + 备选，并写清取舍。

## 关键备注（选型时常踩）

- **流式计算**：引擎底层是 JVM；业务优先 Flink SQL；复杂自定义算子 Java/Scala；简单清洗可用 PyFlink；Go/Rust 一般只做上下游采集，不写核心算子。
- **GUI**：所有语言里 Python 生态断层领先；Ruby、Go、Java 属于「能用，但不适合把界面作为核心卖点」。
- **分层混搭**：
  - 上层业务脚本/工具：Python / Ruby
  - 中台网关、采集服务：Go
  - 核心交易、实时流：Java + Flink
  - 音视频、硬件底层：C/C++
