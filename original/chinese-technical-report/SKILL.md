# 中文技术报告编写

先分清文稿类型，再按「章—节—段 + 图表」组织。正式提交正文与答辩口播稿、队内供料稿是不同体裁。

本 skill 吸收开放生态中若干写法（结构/短句、证据分层、去空话），固定为中文技术/赛题报告语境；细则见 [`structure-and-figures.md`](structure-and-figures.md)。起源于交通拥堵治理 / 规划仿真赛题项目，通用规则可复用；项目特有核对清单见 [`kb-report-sync.md`](kb-report-sync.md)（可按本仓库路径替换为你的真源）。

## When to use

- 写或改中文研究报告、赛题提交材料、附录、技术总结
- 要求「按中文习惯排版」「章—节—段」「图题表题位置」
- 对照规则表 / 知识库 / 样品哈希同步报告口径
- 检查标题是否写了结论、是否混入口播或开发黑话

**When NOT to use**：纯英文论文排版、技术博客（用 `cn-blog-writing`）、与报告无关的代码实现。

## 文稿类型

| 类型 | 典型路径 | 读者 | 正文允许 |
| --- | --- | --- | --- |
| 正式研究报告 | `docs/submission/研究报告.md` | 评委 / 外读 | 章—节—段；图号表号；问题—方法—结果—局限 |
| 附录供料 | `docs/mvp/知识库研究报告附录草稿.md` | 执笔剪贴 | 表、样品、否定句；少过程旁白 |
| 答辩技术总结 | `docs/mvp/知识库技术总结.md` | 口播 / PPT | 可保留「图ID / 口播」块 |
| 案例结果报告 | `docs/reports/**` | 队内 / 附录 | 实验条件、数字、诚实边界 |

**硬边界**：答辩稿里的「结论句 / 口播 / PPT页建议」留在答辩稿；正式研究报告正文用陈述句承载结论。队内状态栏（供料人、@提及、日期催料）放在 README 或文首元数据，定稿前从章节正文剥离。

## 写作步骤

1. **定类型与读者**：上表择一；未说明时默认正式研究报告。
2. **定节契约**：该节目的、允许主张、禁止主张、真源输入（见 structure 文「五问」）。
3. **对齐真源**：知识库相关章节先读 [`kb-report-sync.md`](kb-report-sync.md)，不以旧附录或口播稿为准。
4. **按章—节—段起草**：每节先写中心段，再配图或表，再文内引用「如图× / 见表×」；细则见 [`structure-and-figures.md`](structure-and-figures.md)。
5. **写可核对句**：判断在前；数字带单位与来源；区分「已有数据 / 已确认 / 推断 / 建议」；缺证据写「待验证 / 本窗口未实现」，不补 0。
6. **剥过程旁白**：删「务必写进报告」「供料已并入」「骨架版」等队内指令。
7. **用语与标点自检**：交通术语优先；交通与仿真术语优先；禁用开发黑话堆砌；短句、全角中文标点、术语前后一致。
8. **定稿扫一眼**：章内图号表号连续；图表与正文同口径；否定句仍成立；不确定度未被升级。

## 章—节—段与图表（摘要）

正式报告的最低结构：

```text
### N.M 节标题
　　<中心段：判断 → 依据 → 边界；段首两全角空格>
　　如图 N-x / 见表 N-y ……
<图本体>
<p align="center">图 N-x 题名</p>     ← 图题在图下方居中
<p align="center">表 N-y 题名</p>     ← 表题在表上方居中
<表本体>
　　<可选读法句>
```

| 内容 | 优先载体 |
| --- | --- |
| 流程、分档、空间范围、类—项层级 | 图 |
| 规则/映射/样品/对照数字 | 表 |
| 实测与禁止写法 | 段（可加短表） |

禁止整节只有裸表或只有条列。完整规则与改写策略见 [`structure-and-figures.md`](structure-and-figures.md)。

## 中文表达（正式报告）

### 要

- **判断在前**：段首给结论，再展开。
- **短句为主**：一句一事；过长则拆；少用超长括号链与「首先/其次/最后」套话堆叠。
- **先写是什么**：用肯定句交代对象、范围与做法；边界用「本文覆盖…」「正式对照采用…」收束。
- **客观可核**：写「解析官方既有结果，未执行本次引擎重跑」，少写空泛感受。
- **中文术语优先**：过饱和范围、交通负荷、规划层路网参数、人审前硬校验、对照实验。
- **专名可保留英文**：`rule_id`、`planning_param`、`rule-facts.v1` 等；首次中文释义，后文一致。
- **保不确定度**：把「提示 / 可视为」维持为提示级表述；不新增原文没有的事实与数字。

### 少用「不是×××」「只××」口吻

**非必要不用**下列口吻定义内容或划界：

- 「不是 A」「不等于 B」「并非 C」
- 「只收录 / 只跑 / 只采用 / 只给 / 仅用于」等以「只 / 仅」收窄范围的套话

优先写成肯定陈述，或用「本文覆盖…」「正式路径运行…」「正式对照采用…」标明范围。

| 宜避免 | 宜改为 |
| --- | --- |
| 本交付物不是另拆的源码包 | 本交付物是仓库的结构说明与运行入口 |
| 运行成功不等于治理有效 | 治理成效以正式对照指标与评价证据为准 |
| 历史资料不等于本次正式运行 | 正式对照采用当次批准运行；历史资料供队内复核 |
| 正式对照表只收录真实运行结果 | 正式对照表收录真实运行结果 |
| 正式路径只跑 6 条规则 | 正式路径运行已纳入自动诊断的 6 条规则 |
| 本文只给结构与命令骨架 | 本文给出结构与命令骨架 |

诚实约束仍须守住（见下节）。需要划界时写清正式口径是什么，避免整段用「不是 / 只」开篇或收束。

### 不要（正式正文）

| 现象 | 改写方向 |
| --- | --- |
| 「务必写进报告」「结论句」「口播」 | 删元指令，改成陈述句 |
| 「供料 / 骨架 / 待 @某人」 | 移到 README 或文首状态 |
| 「miss / Worker 直接拒绝」口语夹杂 | 「未命中」；「仿真作业服务拒绝该写法」 |
| 试验性匹配当正式成因 | 标明路径；正式出口单独成表 |
| 开发黑话（夹具、第一刀、禁针、打响） | 见领域用语规则 |
| 图表与正文条数矛盾 | 以现行规则表为准，全文改齐 |
| 悬空图表（无文内引用） | 补「如图× / 见表×」 |
| AI 空话（赋能、抓手、在⋯浪潮中） | 删掉或改成具体对象与动作 |
| 「不是××× / 不等于××× / 只××」堆砌 | 见上节，改成肯定陈述或「本文覆盖 / 正式口径」句 |

答辩技术总结可保留口播块，但块外叙述仍遵守上表「要」。

## 诚实约束（#64，不可破）

1. 无正式评价证据，不写「治理有效」。
2. `is_mock=true` 不进正式对照表。
3. 缺指标写 `null` 或「待」，不补 0。
4. 「运行成功」≠「治理有效」。
5. 未实现能力不写进已完成表述；可写「已支持 / 待开发 / 本窗口未实现」。

## 章节骨架（正式研究报告）

优先沿用 `docs/submission/研究报告.md` 既有九章题名（外读习惯，不用队内黑话作标题）：

1. 研究问题与分析场景 → 2. 总体技术方案 → 3. 拥堵成因诊断 → 4. 规划层治理方案 → 5. 仿真实验设计与实施 → 6. 基准与方案对比分析 → 7. 智能体参与分析过程 → 8. 方法可迁移性 → 9. 结论与局限 → 附录

节标题用完整中文短语标议题（如「成因规则的筛选与分档」「措施边界说明」），**不把结论写进标题**（忌「不予采用」「引擎不消费」「已解决」）。避免「终点分档」「三类闭集」「vs」「HITL」等队内或英文夹杂题名。知识库供料主要落在第 3、4 章与附录；口径冲突时以 `src/kb/rules/` 与 `src/kb/README.md` 为准。

## 完成标准

- [ ] 文稿类型正确；口播/供料元语言未进正式正文
- [ ] 章—节层级连续；关键节有中心段，非裸表
- [ ] 需要处有图或表，且有图号/表号（或明确的图题）与文内引用
- [ ] 知识库相关数字与映射与现行表一致（见 sync 清单）
- [ ] 单位、对象 ID、哈希/指纹可追溯；证据分层未把推断写成已证实
- [ ] 否定句完整；中文通顺；无开发黑话与 AI 空话
