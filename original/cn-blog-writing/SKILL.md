# 中文技术博客编写（掘金 / 知乎）

面向技术推广的技术博客工作流。核心是让文章"有亮点、可信、不像流水账"：结论先行、数据说话、过程留白。

## 使用边界

- **写新博客**：给定主题/素材 → 完整文章。
- **优化已有**：结构、亮点、说服力、篇幅调整。
- **双平台产出**：掘金版（技术向）+ 知乎版（问题导向）。
- 不适用：学术论文、小说散文、营销软文代写。

## 三步工作流

### 第 1 步：探索（挖掘素材）

把输入（复盘、方案、对话、数据、代码）视为原料堆，挖出 fragments 存入草稿文件：

- 数据与结论（带来源）、可复现的命令/代码、真实场景、金句、对比关系。
- 优先捕获 **leading word**：命名整个方案核心的那个词（如"透明转发""打分表"），它会塑造标题、结构与过渡。
- 此阶段只挖掘，不建结构；不编造素材，缺口标"待补充"。

### 第 2 步：节拍（设计骨架）

1. **定 prerequisites**：明确读者进门已懂什么。技术文默认读者 = 工程师（懂 Claude Code / Codex / API / 模型），知乎可放宽到"泛技术读者"。
2. **写 2–3 个候选开头**，每个暗示不同角度（账单痛点 / 悬念 / 直接结论），展示后由用户选定。所选开头决定全文必须兑现的承诺。
3. **规划 beats 路径**：每个 beat 只做一个动作——设场景、给结论、抛数据、转折、收尾。亮点 beat 放中前部（如"便宜 8~42 倍，能力只差 3%"独立成节）。
4. **grounding 检查**：每个新概念（含术语如 Elo、wire_api）必须在引用前出现或被列为前提；未铺垫的术语删数值或补一句解释。

### 第 3 步：塑造（逐段成文）

- 逐段推进，每段回答"读者下一步需要听到什么"，只允许使用已 grounded 的概念。
- **格式论证**：并列项用列表；3+ 同结构用表格；可运行/多行代码用代码块；提示与边注用引用块；长命令用代码块。
- **cut 检查**：每段必须比前段新增价值；与 TL;DR/前文重复的删除；"如果删掉它会破坏什么？"答不上就删。
- 篇幅目标 1500–3000 字；同一信息只保留一个权威版本。

## 硬性红线（违反即失败）

1. **不写流水账**：bugfix 过程、踩坑修复、环境问题叙述一律不进正文——它们拖长篇幅并降低读者信心；只留设计原则与成果。
2. **亮点先行**：最强数据/结论集中成独立章节或表格，开篇即可见。
3. **数字可溯源**：每个数字带来源 URL 或口径声明；查不到标"待补充"；禁止编造。
4. **grounding 纪律**：术语要么先解释，要么删除数值。
5. **配图对应**：封面/题图在标题下；信息图/架构图紧跟对应正文；图片放 `images/` 子目录、Markdown 用相对路径引用，发布时与 md 一起上传。
6. **简体中文**；代码标识符英文；不用 emoji 堆砌。
7. **标题是人话**：标题 = 作者本人会说的话（"人话即标题"），禁止工程化罗列、营销数字轰炸、生造口语比喻。起名方法与检查清单见 `references/title-naming.md`。

## 平台差异

- **掘金**：TL;DR 要点块、代码/表格/架构图密度高、务实工程叙事、结尾可给团队建议。详见 `references/platform-juejin.md`。
- **知乎**：问题导向标题、第一人称叙事、结论先行、数据表格、边界声明、评论区引导。详见 `references/platform-zhihu.md`。
- 方法论细节（fragments/beats/shape 完整规则）见 `references/writing-method.md`。

## 交付前检查清单

- [ ] beats 连贯无断层，开头承诺已兑现
- [ ] 每段都有新增价值（cut 检查通过）
- [ ] 术语已 grounding（无裸奔缩写/数值）
- [ ] 数字带来源/口径，无编造、无"待补充"遗漏
- [ ] 无 bugfix/踩坑流水账叙述
- [ ] 篇幅 1500–3000 字
- [ ] 图片已嵌入对应位置、路径正确
- [ ] 按目标平台惯例微调（掘金 TL;DR / 知乎叙事）
- [ ] 标题通过"人话即标题"检查（`references/title-naming.md` 清单）
